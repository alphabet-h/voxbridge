# 音声まわりの前提

**WAV を触るコードを書く前にこれを読むこと。** ここに書いてある 4 つは、
どれも「数値は正しく見えるのに音だけ壊れている」という形で出る。

## 1. 正規形は 48000 Hz / モノラル / 16bit

唯一の出典は `src/OpenAiWindowsTts/Audio/CanonicalFormat`。**数値を直書きしない。**

サンプルレートだけは**譲れない**。チャンネル数とビット深度は受け側で変換されることが多いが、
サンプルレートを変換しないクライアントは珍しくなく、48000 以外を返すと
**接続はできるのに生成のたびに再試行不可の失敗になる**。原因が最も分かりにくい壊れ方。

## 2. Windows が吐くのは 16000 Hz。ヘッダは 46 バイト

`SynthesizeTextToStreamAsync` の出力は **16000 Hz / 1ch / 16bit 固定**で、
フォーマットを指定する API は存在しない。

そして **`fmt` チャンク長が 18**（`cbSize = 0` が付く）ので、**ヘッダは 44 バイトではなく 46 バイト**。

```
offset 12  "fmt "  18
offset 20  PCM / 1ch / 16000Hz / 32000Bps / blockAlign 2 / 16bit
offset 36  cbSize 0      ← 44 バイト固定のヘッダには無い 2 バイト
offset 38  "data" <size>
offset 46  PCM 本体
```

**44 バイト決め打ちで PCM を切り出すと 2 バイトずれる。** 16bit なので半サンプルのずれになり、
左右のバイトが入れ替わった雑音混じりの音が出る。数値は全部それらしく見えるので、
**耳で聞くまで気づかない。**

必ずチャンクを走査して `data` を探すこと:

```
offset = 12
while (offset + 8 <= length):
    id   = 4 バイト
    size = 4 バイト（リトルエンディアン）
    ... id が "fmt " なら書式、"data" なら本体 ...
    offset = offset + 8 + size + (size % 2)     ← 奇数サイズは 1 バイトのパディング
```

## 3. 16000 → 48000 はポリフェーズ FIR。線形補間は使わない

比が**ちょうど 3 倍**の整数比なので、素直に組める。

| | |
|---|---|
| 位相数 | 3 |
| 窓 | Blackman-Harris か Kaiser（β ≒ 8） |
| タップ数 | 32〜48（位相あたり 11〜16） |
| 遮断周波数 | 7600 Hz 前後（元の Nyquist 8 kHz の少し下） |

**線形補間で済ませない。** 3 倍のゼロ挿入で 16 kHz と 32 kHz にイメージが立ち、
線形補間の減衰では取り切れず、金属的な折り返し音が残る。
「なんとなくシャリつく」という、指摘されるまで気づきにくい劣化になる。

検証は信号を通して測るしかない:

- 1 kHz の正弦波を 16 kHz で作って上げ、**16 kHz と 32 kHz のイメージが十分落ちているか**
- 直流と無音が壊れないか
- **長さが正確に 3 倍になるか**（端の処理で 1 サンプル増減しやすい）

`Audio/` を WinRT にも ASP.NET にも依存させないのは、この検証を書けるようにするため。

## 4. 書き出すときは 44 バイトの標準ヘッダ

読むときは緩く、書くときは厳しく。`fmt` チャンク長 16 の標準形で書く。

**ストリーミングで返すときは RIFF と `data` の size を 0 で書く**（長さが確定していないため）。
WAV のパーサは size が 0 か実バイト数を超えているとき「残り全部」として読むのが通例。

## 5. 長さは必ず実測する

```
blockAlign  = channels * (bitDepth / 8)
frameCount  = dataLength / blockAlign
seconds     = frameCount / sampleRate
```

`Audio/CanonicalFormat.DurationSeconds` がこれ。**エンジンが申告した長さを信じない。**
申告値と実データがずれると、再生位置と波形が食い違って原因が追えなくなる。
