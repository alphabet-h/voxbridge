# 03 Windows の音声合成

> この文書の数値は **2026-08-15 に Windows 11 Pro build 26200 の 1 台**で実測したもの。
> 台数 1 台の観測なので、別の PC で違ったら**この表を疑うのではなく、両方を書く**こと。

## 1. どの API を使うか

Windows から音声合成を呼ぶ道は 2 本ある。**WinRT を使う。**

| | 使える日本語の声 | 出力フォーマット |
|---|---|---|
| **WinRT** `Windows.Media.SpeechSynthesis` | **3 つ** — Ayumi / Haruka / Ichiro | 16 kHz 固定・変更不可 |
| `System.Speech`（SAPI5） | **Haruka Desktop だけ** | `SpeechAudioFormatInfo` で指定できる（48 kHz も直接出る） |

`System.Speech` は出力フォーマットを選べるという利点があるが、**OneCore の声が見えない**。
実測では `System.Speech` から見えたのは `Microsoft Haruka Desktop` と `Microsoft Zira Desktop`（en-US）の 2 つだけだった。

OneCore の声を SAPI5 側へ見せる道具は存在するが、**利用者に別途インストールを強いる**。
「置いて叩くだけ」を壊すので採らない。

**3 声を取り、リサンプルは自分でやる。**

## 2. この PC の声

```
ayumi   Microsoft Ayumi    ja-JP  Female   MSTTS_V110_jaJP_AyumiM
haruka  Microsoft Haruka   ja-JP  Female   MSTTS_V110_jaJP_HarukaM
ichiro  Microsoft Ichiro   ja-JP  Male     MSTTS_V110_jaJP_IchiroM
```

`VoiceInformation.Id` の実体は `HKEY_LOCAL_MACHINE\SOFTWARE\Microsoft\Speech_OneCore\Voices\Tokens\...` という
レジストリのフルパス。**API に載せるには長すぎる**ので、表示名から短い id を作る
（`Speech/VoiceCatalog.MakeId`）。

`--list-voices` で同じ一覧が出る。

## 3. 出力フォーマット — ここが設計を決めた

`SynthesizeTextToStreamAsync` が返すストリームの中身:

| | |
|---|---|
| `ContentType` | `audio/wav` |
| サンプルレート | **16,000 Hz** |
| チャンネル | 1 |
| ビット深度 | 16 |
| `fmt` チャンク長 | **18**（`cbSize = 0` が付く） |
| `data` チャンクの開始 | offset **38** |
| PCM 本体の開始 | offset **46** |

**フォーマットを指定する API は存在しない。** `SpeechSynthesizerOptions` に該当する項目が無い（§4）。

ここから 2 つ決まる:

1. **48 kHz へ 3 倍にアップサンプルする必要がある**（[02](02-http-contract.md) §5.2）
2. **ヘッダは 44 バイトではなく 46 バイト。** 44 バイト決め打ちで PCM を切り出すと 2 バイトずれて、
   全体が半サンプルずれた雑音混じりの音になる。**必ずチャンクを走査して `data` を探すこと**

実際のヘッダ（先頭 46 バイト）:

```
52 49 46 46 a6 19 02 00  RIFF <size>
57 41 56 45              WAVE
66 6d 74 20 12 00 00 00  "fmt " 18
01 00                    PCM
01 00                    1ch
80 3e 00 00              16000 Hz
00 7d 00 00              32000 byte/s
02 00                    blockAlign 2
10 00                    16bit
00 00                    cbSize 0     ← 44 バイト固定のヘッダには無い 2 バイト
64 61 74 61 80 19 02 00  "data" <size>
```

## 4. `SpeechSynthesizerOptions`

| プロパティ | 型 | 既定 | 使うか |
|---|---|---|---|
| `SpeakingRate` | double | 1.0 | **使う。** `speed` を写す |
| `AudioVolume` | double | 1.0 | 使わない（音量は呼ぶ側で） |
| `AudioPitch` | double | 1.0 | 使わない |
| `AppendedSilence` | enum | `Default` | 使わない。`Default` / `Min` の 2 値しかなく、数値では指定できない |
| `PunctuationSilence` | enum | `Default` | 同上 |
| `IncludeWordBoundaryMetadata` | bool | false | いまは使わない。字幕の時刻を出す口としては見込みがある |
| `IncludeSentenceBoundaryMetadata` | bool | false | 同上 |

### `SpeakingRate` の有効域 — ドキュメントと実測が違う

**setter は値を検証しない。** 0.2 も 8.0 も例外を投げずに通り、読み返すとその値が返ってきます。
Microsoft のドキュメントは有効域を **0.5〜6.0** と書いていますが、**実測すると下限が違いました**。

同じ文で計測（2026-08-15）:

| rate | 長さ | 有声区間の割合 |
|---|---|---|
| 0.2 | 24.23 s | 57.5% |
| 0.25 | 19.41 s | 57.4% |
| 0.3 | 16.16 s | 57.7% |
| 0.5 | 9.72 s | 57.5% |
| 1.0 | 4.89 s | 57.1% |
| 6.0 | 1.08 s | 59.3% |
| **6.5** | **1.08 s** | — ← ここから丸められる |
| **8.0** | **1.08 s** | — |

**下限は 0.2 まで連続に効きます。** 長さが 1/rate にほぼ比例し、有声区間の割合が
57.5% で一定なので、無音で引き伸ばしているのではなく本当にゆっくり喋っています。
**丸められるのは上限 6.0 超だけ**でした。

> **クランプの下限を 0.5 にしてはいけない。** 契約が受ける `speed: 0.25` が
> `0.5` とバイト単位で同一の WAV を返すようになり、
> **「設定できたのに効かない」がクランプのせいで起きます。**
> 実装は下限 0.2 / 上限 6.0（`Speech/SpeechEngine`）。

## 5. 合成は同時に呼べない — 呼ぶとプロセスが落ちる

**OneCore の合成エンジンは、プロセス内で同時に走らせられません。**
`SpeechSynthesizer` のインスタンスを分けても駄目です。

同時に叩くと、例外ではなく **`__fastfail`** でプロセスごと落ちます。

```
Faulting application name: voxbridge.exe
Faulting module name: MSTTSEngine_OneCore.dll, version: 10.3.21207.0
Exception code: 0xc0000409          ← STATUS_STACK_BUFFER_OVERRUN
```

**例外ではないので try/catch にもログにも一切かかりません。** 落ちた瞬間に走っていた
全リクエストが接続断になり、以降は接続拒否になります。

実測（2026-08-15・HTTP 経由）:

| 条件 | 結果 |
|---|---|
| 同時 1 本、320 件 | 完走 |
| 同時 2 本、25 ラウンド × 6 並列 | **17 ラウンド目で死亡**（exit 3221226505） |
| 同時 4 本、20 ラウンド × 8 並列 | **12 ラウンド目で死亡** |

WinRT だけに絞った切り分け:

| やり方 | 結果 |
|---|---|
| リクエストごとに new / Dispose | 25 回・1.1 秒で死亡 |
| インスタンスを使い回す | 約 180 回・3.3 秒で死亡 |
| **`SemaphoreSlim(1,1)` で直列化** | **430 回・25 秒 完走** |

壊しているのは生成・破棄の競合ではなく、**合成呼び出しそのものの同時実行**です。

**死ぬ手前でも壊れます。** 並列時は同じ文・同じ声でも**バイト列の違う音声**が返ります
（長さは同じで中身だけ違う。同時 4 本で 61 件中 18 件）。

> **対処: `Speech/SpeechEngine` の中で `static SemaphoreSlim(1,1)` により直列化してあります。**
> 設定で変えられるようにしないこと。`--concurrency` は「同時に受け付けるリクエスト数」で、
> 合成そのものは常に 1 本ずつです。
> 回帰テストは `SpeechEngineTests.並列に呼んでもプロセスが落ちない`。

## 6. プロセス最初の 1 回だけ音が違う

起動後 1 回目の合成だけ、同じ入力・同じ声でも 2 回目以降と違う音を返します。
**長さは同じ**なので自動テストでは捕まりません（実測: 132,960 サンプル中 94,463 が不一致、
最大偏差 3,880 ＝ フルスケールの約 12%）。

対処: 起動時に捨て合成を 1 回入れてあります（`SpeechEngine.WarmUpAsync`）。

**裏取り**（2026-08-15）: ウォームアップを入れる前に書き出しておいた 3 声の WAV と、
入れた後の出力を突き合わせたところ、**その回で 1 番目に合成した声だけが不一致**で、
2 番目・3 番目はバイト単位で完全に一致しました。
不一致になった声も、プロセスを変えて何度叩いても同じバイト列を返します。
**「1 回目だけ違う」が実在し、ウォームアップで消えている**ことがこれで確定しています。

### 6.1 中断のあとの 1 回も違う

同じ揺れが**中断の直後にも起きます**（2026-08-16）。150 件の合成を 60 ms で abort したあと、
基準と同じ入力・同じ声で合成すると、**直後の 1 回だけ違うバイト列**が返り、
2 回目からは基準に戻ります。

これは合成器を使い回すかどうかとは**無関係**です。3 方式で同じ負荷を通して確かめました:

| | プロセス | 中断直後の音 |
|---|---|---|
| 毎回 `new` する | 落ちない | **1 回だけ違う** |
| 声ごとに使い回す（中断で捨てない） | 落ちない | **1 回だけ違う** |
| 声ごとに使い回す（中断で捨てる） | 落ちない | **1 回だけ違う** |

差が出ないので、**中断で合成器を捨てていません**（§7.2）。
中断が来るのはクライアントが切った時なので、その 1 回の音は誰も聞きません。

> **テストで「中断のあとも同じ音」を期待しないこと。** それは実装ではなく
> Windows 側の性質を検査することになり、負荷の掛かり方で赤くなったり緑になったりします。
> `SpeechEngineTests.中断のあとでも合成を続けられる` は「直後の 1 回」を捨ててから比べています。

## 7. 速さ

> **数字はすべて Release ビルド・ウォームアップ後の中央値**（2026-08-15 に測り直し。
> 端から端までの表は合成器を使い回すようにした 2026-08-16 に測り直し）。
> 測り方の注意は §7.1。

| | |
|---|---|
| **合成** | **0.90 ms/文字**（音声 1 秒あたり 3.8 ms。RTF ≒ **0.004**） |
| **48 kHz へのアップサンプル** | **0.77 ms/音声1秒**（0.18 ms/文字）。合成の **約 20%** |
| PCM のバイト列化 | 0.08 ms/音声1秒 |
| **合わせて** | **約 1.1 ms/文字** |
| 発話の長さ | **0.24 秒/文字** 前後（日本語・speed 1.0） |
| GPU | 不要 |
| `powershell.exe` の起動 | **1,834 / 2,180 / 2,606 ms**（3 回計測） |

端から端まで（HTTP 経由・Release・合成器を使い回した後）:

| 入力 | ヘッダまで | 返し方 |
|---|---|---|
| 20 文字 | **21 ms** | `Content-Length` 付き |
| 200 文字 | 165 ms | `Content-Length` 付き |
| 1,000 文字 | **817 ms** | `Content-Length` 付き（分割の閾値ちょうど） |
| 3,000 文字 | **173 ms** | チャンク転送 |
| 6,000 文字 | **178 ms** | チャンク転送 |

**1,000 文字より長い入力のほうがヘッダが速く返る**のは、そこからチャンク転送に切り替わるため。
チャンク転送の設計が効いていることが、この 2 行の逆転に出ている。

**本文を最後まで受け取るまでの時間は測っても意味が無い。** 6,000 文字は 124 MB あり、
同じビルドの同じ入力でも 5.5〜10.4 秒とばらつく。支配しているのは合成ではなく転送。

**プロセス起動が合成の 15〜22 倍かかる**ので、「都度コマンドを叩く」方式は成立しない。
常駐サーバにする根拠はここ（[01](01-overview.md) §2）。

合成がこれだけ速いので、進捗を SSE で刻む意味はほぼ無い（[02](02-http-contract.md) §4.2）。

ただし **1.1 ms/文字は無限に速いわけではない**。全部合成してからヘッダを返す実装だと、
接続タイムアウト 15 秒に**約 13,000 文字**で届く。長文でヘッダを先に返す理由はここ
（[02](02-http-contract.md) §4.3）。

### 7.1 測り方を 2 回間違えた

**この表の数字は 2 回作り直しています。** 同じ間違いをしないために残します。

| 間違い | どう狂ったか |
|---|---|
| **Debug ビルドで測った** | リサンプラが **4.7 倍**遅く出る（6.19 → 1.32 ms/音声1秒）。「変換が合成の 160%」という結論まで反転する。**出荷するのは Release。測るのも Release** |
| **ウォームアップせずに 1 回だけ測った** | 合成の初回は WinRT の初期化を含む。1 文で 198 ms 出たが、温まると 0.90 ms/文字（640 文字で 575 ms） |

「リサンプラが合成時間の 3〜4 割」という以前の記述は、この両方を踏んだ数字でした。
**プローブで測るときは、Release で、3 回捨ててから中央値を採ること。**

### 7.2 合成器は声ごとに使い回す（2026-08-16 に測って決めた）

`SpeechSynthesizer` をリクエストごとに作って捨てていた頃は、
**生成と破棄だけで 19〜23 ms** かかっていた。20 文字の合成が 41.8 ms だったので、
**半分以上が合成以外**だった。

| 20 文字を 1 回・同じ声 | |
|---|---|
| 毎回 `new` する | 41.8 ms |
| 1 つを使い回して `Voice` を代入 | 15.9 ms |
| 声ごとに持つ | 16.5 ms |

**声を切り替えると話が変わる。** `Voice` の代入そのものは 0.001 ms だが、
**代入した次の合成が 2 倍以上遅くなる**（内部でエンジンを切り替えている）。
1 つを使い回す方式は、ここで効果の大半を失う。

| 20 文字を 1 回・3 声を巡回 | |
|---|---|
| 毎回 `new` する | 50.4 ms |
| 1 つを使い回して `Voice` を代入 | 33.0 ms |
| **声ごとに持つ** | **14.3 ms** |

だから**声ごとに 1 つ持って使い回す**。1 つあたり約 1.1 MB（20 個作って測った）。
使われた声の分しか作らないので上限は設けていない。

**中断では捨てない。例外のときだけ捨てる。**
中断で捨てても §6.1 のとおり音の揺れ方は変わらず、150 件 abort の負荷でも落ちなかった。
差が無いなら捨てないほうが速い。例外のときに捨てるのは実測ではなく安全側の判断で、
壊れた合成器を持ち続けると**1 回の失敗が以後の全リクエストに伝染する**ため。

> **触ってよいのは `SynthesisLock` を持っている間だけ。** 共有の可変状態なので、
> lock の外から触ると壊れる。§5 の直列化と寿命を揃えてあるのはそのため。

## 8. 分割の継ぎ目 — 測ったら問題なかった

チャンクごとに `SynthesizeTextToStreamAsync` を呼ぶので、
**境界に無音が積み増されるのではないか**という懸念があった。実測した（2026-08-15）。

同じ文を 10 個並べた 160 文字を 1 回で合成した結果:

| | |
|---|---|
| 先頭の無音 | **170 ms** |
| 末尾の無音 | **910 ms** |
| 文と文の間（9 箇所） | **すべて 1,080 ms**（ばらつきゼロ） |

つまり分割したときの継ぎ目は **910 + 170 = 1,080 ms** で、
**文と文の自然な間とちょうど同じ**。

> **結論: 無音のトリムは実装しない。** 文の区切りでしか分割しないので、
> 継ぎ目は自然な間と区別がつかない。

**ただし例外がある。** 1,000 文字の中に文の区切りが 1 つも無いテキストは、
読点や空白、最後は文字数で強制的に切る（[02](02-http-contract.md) §4.3）。
その場合は**文の途中に 1,080 ms の間が入る**。区切りの無い長文を渡したときだけ起きる。
気になったら、そのときにトリムを検討する。

計測は 10 ms 窓の RMS が 150 未満を「無音」として数えた。

## 9. API の面

`SpeechSynthesizer` が持つメソッドは 2 つだけ。

- `SynthesizeTextToStreamAsync(string)`
- `SynthesizeSsmlToStreamAsync(string)`

SSML は受け付けない方針（[01](01-overview.md) §5）。利用者の本文がそのまま
マークアップとして解釈される口を開けると、`<` を含むテキストで壊れる。

静的プロパティ:

- `SpeechSynthesizer.AllVoices` — 全部の声
- `SpeechSynthesizer.DefaultVoice` — Windows の既定（表示言語に追随する）

**既定の声はここから取る。** 「日本語の声を優先する」のような細工をこちらで入れると、
起動ログに出ている声と実際に喋る声が食い違ったときに理由が追えなくなる。
選びたければ `--voice` で明示する。

## 10. 確認のしかた

PowerShell から声の一覧だけなら:

```powershell
$null = [Windows.Media.SpeechSynthesis.SpeechSynthesizer, Windows.Media, ContentType=WindowsRuntime]
[Windows.Media.SpeechSynthesis.SpeechSynthesizer]::AllVoices |
  ForEach-Object { "{0} | {1} | {2}" -f $_.DisplayName, $_.Language, $_.Gender }
```

合成まで確かめるなら、`WindowsRuntimeSystemExtensions.AsTask` を反射で引いて
`IAsyncOperation` を待つ必要があり、PowerShell 5.1 では手数が多い。
**素直に `dotnet run -- --list-voices` を使うほうが早い。**
